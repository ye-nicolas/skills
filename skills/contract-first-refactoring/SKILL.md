# Contract First Refactoring

先從責任邊界與方法契約判斷設計，再修改程式碼。使用者提到的
`Optional`、`boolean`、方法名稱或某個局部改法只是待驗證的方向，不要把它
當成設計前提。除非使用者明確要求改變業務規則，否則保留既有業務流程、
執行順序、可觀察副作用與錯誤語意。

## 適用範圍

這個 skill 適用於以下類型的重構：

- 查詢、驗證、決策、狀態變更或外部呼叫混在同一個方法中。
- 方法回傳型別、方法名稱、例外處理與實際行為不一致。
- 使用者要求「簡化」API，但目前程式可能具有 `null`、缺值、未知狀態、
  驗證失敗或例外等多種結果。
- 需要在不改變既有業務流程的前提下拆分責任或整理控制流程。

若需求只是全域機械式改名、格式化、lint 修正或明確指定且不涉及語意的
型別替換，不要套用完整流程。

## 工作模式與修改粒度

這個 skill 用於實際修改 code，但要先區分設計分析與實作重構：

### 設計分析

若使用者要求分析「應該如何調整」、比較設計或評估責任分離，可以提出不受
最小 diff 限制的理想完整設計。此時不必為了避免改太多而壓縮或扭曲設計，
但要清楚區分：

- 理想設計：責任、API 與長期結構應如何安排。
- 落地方案：在既有程式上實際修改時，哪些是必要的最小變更。

### 實作重構

若使用者要求實際修改、實作或重構，預設只做必要的最小變更：

- 先限定在目標方法、直接受影響的呼叫者、必要的測試與契約文件。
- 不順手重排格式、改無關命名、搬移套件、替換框架、重寫既有 helper，或
  同時處理其他技術債。
- 只有當相鄰程式碼直接阻礙契約一致性、編譯、測試或安全執行時，才納入同
  一個變更，並說明它與目標重構的必要關係。
- 發現但不影響本次契約的問題時，保留原狀並另行列出，不要偷渡到同一個
  diff。
- 只有在使用者明確要求擴大重構、完整整理或依理想設計改寫時，才放寬實作
  粒度；仍須說明新增範圍與行為風險。

## 工作流程

### 1. 先建立現況契約

在修改前，閱讀目標方法、所有重要呼叫點、相關 DTO/entity/schema、驗證器、
例外類別、測試與設定。用實際程式碼確認，不要只依方法名稱推測。

至少整理出：

- 輸入條件、前置條件與 `null`/缺值語意。
- 所有有意義的結果，包括成功、否定結果、缺值、未知狀態、驗證失敗與
  外部操作失敗。
- 回傳值如何被每個呼叫者使用，以及呼叫者是否需要區分那些結果。
- 查詢、驗證、決策、狀態變更、通知或其他外部呼叫的順序。
- 哪些副作用已經發生、哪些例外會被拋出、轉換或讓它向上傳遞。
- 交易、重試、冪等性、快取或鎖等會讓順序具備語意的邊界。

不要只分析 HTTP 200 或 happy path；每一個會影響呼叫者、狀態或控制流程的
分支都屬於契約的一部分。

### 2. 劃分責任與控制流程

把現有流程按語意標記為「取得資料」、「驗證」、「做決策」、「執行副作用」
與「處理/映射例外」。指出一個方法同時承擔哪些責任，以及每個責任應由哪
一層或哪個方法擁有。

特別檢查：

- 查詢結果的缺值是否是正常業務狀態，還是資料不一致/錯誤。
- 驗證是在查詢前、查詢後或副作用前發生；移動它是否改變可觀察行為。
- 例外是預期的業務分支、輸入錯誤、基礎設施錯誤，還是程式缺陷。
- 方法名稱是否描述它真正負責的動作，而不是描述其中一個偶然實作細節。

### 3. 從語意決定 API 形狀

在責任與結果狀態清楚後，才選擇回傳型別與方法名稱：

- 只有當領域確實只有兩種結果，且呼叫者不需要區分缺值或未知狀態時，才
  使用 `boolean`。
- 若「沒有結果」本身是合法且需要由呼叫者處理的狀態，才使用
  `Optional<T>` 或等價的明確缺值表示；不要用它包裝其實只有二元語意的
  布林值。
- 若失敗代表違反前置條件、輸入無效、資料不一致或外部資源失敗，依既有
  邊界與專案慣例保留或明確映射例外，不要為了讓簽名看起來簡單而吞掉例外。
- 方法名稱應表達擁有的責任與語意；查詢、判斷、驗證與執行動作不要用同一
  個模糊名稱混在一起。

如果狀態模型仍有歧義，先列出最小的候選設計與各自會改變的呼叫者行為，
再採用有證據的方案；若無法安全推斷，向使用者提出一個具體的阻塞問題。

### 4. 做最小且一致的重構

優先採用能讓責任清楚、但不改變既有行為的最小變更，例如抽出一個真正有
單一責任的私有方法、調整公開方法名稱與型別，或讓例外在正確的邊界處理。
同步更新所有呼叫者、測試與文件中的契約。

除非需求明確包含行為變更，必須維持：

- 業務決策與流程順序。
- 驗證時機、失敗條件與可觀察的錯誤語意。
- 副作用的發生與順序，包括事件、通知、寫入、遠端呼叫與快取。
- `null`、缺值與例外的處理方式。
- 交易、重試、冪等性與執行緒安全邊界。

不要為了配合新回傳型別而偷偷改變驗證規則、把例外改成 `false`、延後副
作用，或把多種失敗狀態壓成同一種結果。

## 交付格式

在修改前，用簡短內容說明：

1. 現況契約：輸入、結果狀態、副作用、例外與呼叫者依賴。
2. 責任問題：哪些語意目前混在一起，哪個邊界需要調整。
3. 最小設計：方法名稱、回傳型別、驗證位置與例外責任，以及為何符合
   實際狀態模型。

完成後說明：

- 修改了哪些責任邊界與呼叫點。
- 實際修改範圍，以及刻意沒有順手處理的相鄰問題。
- 哪些既有流程與語意刻意保留。
- 針對成功、否定結果、缺值、驗證失敗與例外路徑的驗證結果。
- 使用的編譯、測試或其他專案驗證命令；若未執行，說明原因。
